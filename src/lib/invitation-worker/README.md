# Invitation worker contract

This directory is decision-independent groundwork for the accepted invitation-bound email flow. It contains pure provisioner and delivery contracts, strict runtime validation, deterministic token derivation, and test-only in-memory fault-injection doubles. `index.ts` exports only the production-neutral contracts; tests must import doubles directly from `test-support.ts` so they cannot be mistaken for production adapters.

Worker-only Supabase coordinator and Auth Admin adapter modules are present but deliberately not exported by `index.ts` and are not imported by the Next application. The Auth adapter provisions new users through Supabase's administrative invite endpoint, leaving them unconfirmed while Supabase sends the separate one-time Auth confirmation message; it converges an ambiguous response through an exact normalized-address lookup. For an exact existing confirmed user it sends a no-create passwordless sign-in code, and for an exact orphaned unconfirmed user it renews the administrative invite. This preserves disabled public signups while making reinvitation and stale-code recovery usable. The coordinator adapter requires a dedicated ordinary Auth worker token with a real session identifier—not a service credential or a sessionless signed JWT—for database RPCs; the database rechecks that session and the worker allowlist. These adapters contain no environment loader, credential, queue runner, HTTP endpoint, email provider, deployment configuration, or automatic activation; the default worker contracts still fail before touching a dependency.

A production worker must be deployed separately from the web application. It must load work only by opaque durable IDs, keep versioned token keys and the Auth Admin credential outside the repository and web environment, enforce provider idempotency, and implement every coordinator authorization/compare operation atomically as documented in the contracts. The pre-provider atomic coordinator read—not a separate directory lookup—must return the exact normalized recipient and an opaque recipient binding from the same authoritative snapshot. A newly provisioned target is deliberately unconfirmed until its Auth invitation code succeeds. The binding must change whenever address or confirmation authority changes, and completion must compare it exactly.

Production activation also requires a durable single-flight claim for Auth-code issuance. The local provisioner currently sends the Auth code before database completion; a crash or concurrent invocation can therefore cause a later retry to issue a newer code. Supabase rate limiting is not treated as a correctness boundary. Keep both invitation capability gates disabled until hosted tests prove claim recovery plus delayed and out-of-order message behavior.

Every authorized coordinator seam must also prove that the target Auth user is not already active in the same circle. After materialization, loss of requester authority, recipient confirmation/binding, or target eligibility must atomically invalidate both the durable job and invitation; merely returning an error is insufficient because the bearer token must stop working.

`authorizationVersion` is an opaque database compare value. Adapters and workers must preserve its exact text, including valid microseconds or RFC3339 offsets, and must never parse, normalize, truncate, or re-emit it.

Email delivery cannot participate in the database authorization transaction. The contract therefore reauthorizes immediately before the provider call and again inside atomic completion. If revocation lands in that final network race, an email may already have been accepted, but completion must fail and the durable coordinator must have invalidated the invitation so the link grants nothing.

The provider receipt also binds the SHA-256 of the exact accepted email payload. A plain SMTP adapter without durable idempotency is suitable only for the isolated Mailpit integration harness, never production activation.
